Reviewed: 2026-08-24
Live publication run window used: `2026-08-24` → `2026-12-31`

This document is the human-readable companion to the committed product
publication artifact:

- `data/public/lisbon-porto-map.json` — the canonical, product-facing
  publication artifact the public homepage reads. Regenerated by
  `npm run publish:map-data -- --from=YYYY-MM-DD --to=YYYY-MM-DD`.

**The public homepage does not scrape venue websites. It renders the
latest successfully published map dataset.**

## 2. New publication artifact

`data/public/lisbon-porto-map.json` — a new, deliberately MINIMAL,
product-facing artifact. Shape:

```json
{
  "generated_at": "2026-08-24T21:38:31.645Z",
  "window": { "from": "2026-08-24", "to": "2026-12-31" },
  "source_report": { "success_count": 13, "failure_count": 0, "sources": [ ... ] },
  "counts": { "observation_count": 299, "display_listing_count": 266, "map_marker_count": 12 },
  "countries": {
    "Portugal": { "markers": [ { "venue_id", "canonical_name", "latitude", "longitude", "address", "display_listings" }, ... ] },
    "Croatia": { "markers": [] }
  }
}
```

Each marker uses the existing public `MapMarker` shape as far as possible
(`components/DiscoveryMap.tsx`): `venue_id`, `canonical_name`,
`latitude`, `longitude`, `address`, `display_listings`. The raw, ungrouped
per-Observation `listings` array (used only for internal proof/debug
accounting elsewhere in this repository) is deliberately dropped — every
customer-facing fact is already present in `display_listings`, which is
passed through completely unchanged from the existing display pipeline
(`kind`, `title`/`display_title`, `start`, `end`, `source_id`/
`source_name`, `event_url`, and, for an associated `GROUP`, `sources[]` +
`fact_comparison`). No new Event model was invented, and no Observation
facts were collapsed beyond the already-governed
Hot Clube ↔ Capitólio association layer.

Croatia is always published with an empty marker list: this repository
has no Croatian source registry, no Croatian venues, and no Croatian
Observations — nothing was fabricated to fill it.

## 3. Generator command

```
npm run publish:map-data [-- --from=YYYY-MM-DD --to=YYYY-MM-DD]
```

Implemented by `ingestion/publish-map-data/run.mjs`. It performs live
acquisition from all 13 currently active Lisbon+Porto sources (via
`acquireLisbonPorto()`, unchanged, reused from
`ingestion/lisbon-porto/run.mjs` — the same function `npm run
ingest:lisbon-porto` and `npm run onboard:venues` already use), then
builds and atomically publishes the artifact.

This command performs live HTTP acquisition and must only ever be run
explicitly by an operator or, later, a scheduler. It is never invoked by
`npm run build`, `npm test`, or ordinary page rendering.

## 4. Source/display pipeline — ONE pipeline, not two

`ingestion/map/publication.mjs`'s `buildPortugalMarkers()` is a thin
wrapper that combines the Lisbon and Porto Observation/venue/source-
registry halves and calls the SAME
`projectObservationsToDisplayMarkers()` (`ingestion/map/
group-associated-listings.mjs`) and `resolveVenueMapCoordinates()`
(`ingestion/map/projection.mjs`) already used by every other real
display/map surface in this repository. It therefore automatically
respects, with no duplicated logic:

- canonical `CONFIRMED` coordinates (highest precedence);
- canonical `GEOCODED` coordinates;
- `MANUAL_OPERATOR_ENTRY` coordinates (only for `ADDRESS_ONLY` venues,
  never overriding `CONFIRMED`/`GEOCODED`);
- data-driven venue resolution (`ingestion/venue/resolver.mjs`);
- the existing Hot Clube ↔ Capitólio association rule
  (`ingestion/association/hot-clube-capitolio.mjs`);
- the current source registry (`sources/lisbon.json`, `sources/porto.json`)
  and all 13 existing source collectors, completely unchanged.

No second, homepage-only map projection path was written.

## 5. Manual-coordinate integration

`ingestion/publish-map-data/run.mjs` loads
`venues/manual-coordinates.json` read-only, via the existing
`loadManualCoordinateStore()` (`ingestion/geocoding/
manual-coordinate-store.mjs`), and forwards it unchanged into
`buildPortugalMarkers()`. The file is never edited, never geocoded
against, and no canonical Venue `location_status` is ever changed by this
package. All 7 currently committed human manual entries (Village
Underground Lisboa, BOTA Anjos, Super Bock Arena, Galeria Zé dos Bois,
LAV, Centro Cultural Malaposta, Biblioteca Municipal D. Dinis) are
consumed exactly as today's real map/display surface already consumes
them — see `tests/publication-artifact.test.mjs` tests 4–6 and 16 for the
deterministic proof of this (including that a stale manual entry never
overrides `CONFIRMED`/`GEOCODED` coordinates).

## 6. Atomic publication rule

`ingestion/map/publish-artifact-io.mjs`'s `writePublicationArtifactAtomic()`:
temporary sibling file → `validatePublicationArtifact()` (schema +
internal cross-check) → fsync → close → atomic `rename()` onto
`data/public/lisbon-porto-map.json`. Validation runs BEFORE any temp file
is opened, so a schema-invalid artifact is refused immediately and the
previously committed file is never observed partially written and never
replaced by a broken one. No abandoned temp file is ever left behind on
success (`tests/publication-artifact.test.mjs` tests 14–15).

## 7. Catastrophic-run preservation rule

A publication run is **catastrophic** — and must never replace the
previously committed artifact — when EITHER:

- zero of the 13 sources succeeded, OR
- the resulting Portugal map marker count is zero.

A run where at least one source succeeds and produces at least one map
marker is publishable, even if other sources failed — consistent with
this project's existing per-source try/catch isolation
(`ingestion/lisbon-porto/run.mjs`'s `acquireAll()`). No additional
availability threshold (e.g. "N of 13 sources must succeed") was
invented. See `isCatastrophicPublicationRun()` in
`ingestion/map/publication.mjs` for the single, authoritative
implementation of this rule, and `ingestion/publish-map-data/run.mjs`,
which exits non-zero without ever calling the atomic writer when this
rule trips.

## 10. Handoff point for the future scheduler

`npm run publish:map-data` (or, if the future scheduler runs in-process,
`buildPortugalMarkers()` + `buildPublicationArtifact()` from
`ingestion/map/publication.mjs` plus `writePublicationArtifactAtomic()`
from `ingestion/map/publish-artifact-io.mjs`, called directly) is the one
clear command/function set `BOTM-SOURCE-SCHEDULER-01` should call on
whatever cadence it chooses. It:

- performs the exact same 13-source live acquisition already proven;
- refuses to publish a catastrophically empty/broken run (rule above);
- validates and atomically replaces `data/public/lisbon-porto-map.json`
  only on a good run;
- requires no other change anywhere else in the codebase — the public
  homepage always reads whatever this command last successfully wrote.

No cron, GitHub Actions schedule, Vercel Cron, background worker,
database, or periodic polling was added by this package — it only
establishes the publication boundary a scheduler will call later.

## Deferred / out of scope (explicit)

- **Date filtering**: the homepage's From/To controls remain
  presentational, exactly as before. Wiring them to filter publication
  listings in the browser was assessed as secondary per this task's own
  brief ("Do not let date-filter feature creep jeopardize this package")
  and was deferred rather than risk the primary publication-wiring
  objective.
- **Genre/Type/Price controls**: left exactly as decorative/non-functional
  as before — no fabricated filtering was added, since the current
  Observation/publication model does not reliably carry this metadata.
- **List view**: unchanged. It already shares the same `visibleMarkers`
  state as the map view (only a CSS class toggles), so it automatically
  inherits the new publication data with no separate work required.
- The 12 outstanding coordinate exceptions, the association rules, the 13
  source collectors themselves, and any scheduler/cron infrastructure are
  all explicitly out of scope for this package and were not touched.
