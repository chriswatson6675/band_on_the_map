# Operator Venue Coordinates (VENUE-MANUAL-COORDINATES-DASHBOARD-01)

A small, local, single-purpose operator dashboard for clearing the
manual-coordinate exception queue: canonical Venues that are evidenced
(`ADDRESS_ONLY`) but have no first-party coordinates, and never will
without a human deciding one is good enough for the map. This is
intentionally **not** a full admin suite — no source management, no
scheduling, no auth beyond a local/production write gate, no database, no
geocoding, no event editing.

**Manual operator coordinates are persisted in
`venues/manual-coordinates.json`.**

## 1. Canonical locations

| Concern | Path | Authoritative? |
|---|---|---|
| Dashboard source code | `app/operator/venues/page.tsx` (server component) + `components/OperatorVenuesDashboard.tsx` (client) + `app/api/operator/manual-coordinates/route.ts` (write endpoint) | — (code, not data) |
| Manual coordinate store | `venues/manual-coordinates.json` | **Yes — the only authoritative store for operator-entered coordinates** |
| Generated outstanding queue | `fixtures/geocoding/manual-coordinate-queue.json` (`npm run report:manual-coordinate-queue`) | No — derived/report-only, regenerated from live data |
| Canonical Venue identity/address | `venues/lisbon.json`, `venues/porto.json` | Yes, for identity/address/CONFIRMED-GEOCODED coordinates |
| Live per-venue "waiting listings" numbers | `fixtures/map/lisbon-porto-overnight-coverage-01-live-run-proof.json` (`npm run ingest:lisbon-porto`) | Derived proof, regenerated by that live-run script |

Persistence logic itself lives in
`ingestion/geocoding/manual-coordinate-store.mjs` (read/validate/atomic
write/remove), `ingestion/geocoding/operator-write-gate.mjs` (the
production/hosted-deployment write gate — absolutely denies both Vercel
and Netlify, see §4), and
`ingestion/geocoding/venue-coordinate-dashboard.mjs` (assembles the
dashboard's view model from the live estate). Map coordinate composition
(canonical vs. manual precedence) lives in
`resolveVenueMapCoordinates()` in `ingestion/map/projection.mjs`.

## 2. Source-of-truth hierarchy

1. **Canonical Venue identity/address** — `venues/lisbon.json` /
   `venues/porto.json`. Never touched by this dashboard.
2. **Authoritative canonical coordinates** — a Venue's own `CONFIRMED` or
   `GEOCODED` `latitude`/`longitude` (see
   `ingestion/venue/contract.mjs`). Always wins over a manual entry.
3. **Manual operator map-coordinate overrides** —
   `venues/manual-coordinates.json`. Used for map placement ONLY when
   step 2 does not apply to that venue.
4. **Generated outstanding exception queue** —
   `fixtures/geocoding/manual-coordinate-queue.json`. Derived, never
   authoritative — regenerating it never invents or removes canonical
   data; it only reports which venues from step 1 still lack both step 2
   and step 3. This relationship is never reversed: the generated queue
   is read FROM the canonical data, never written back INTO it.

## 3. Manual provenance and semantics

A manual entry never masquerades as `CONFIRMED` or `GEOCODED`, and never
mutates the canonical Venue record. `ingestion/venue/contract.mjs`'s
`LOCATION_STATUSES` remains exactly `{CONFIRMED, GEOCODED, ADDRESS_ONLY,
UNRESOLVED}` — this package adds no fifth status. A venue stays
canonically `ADDRESS_ONLY` while it acquires map coordinates through
`venues/manual-coordinates.json`.

Each entry:

```json
{
  "venue_id": "venue-lisboa-example",
  "latitude": 38.123456,
  "longitude": -9.123456,
  "method": "MANUAL_OPERATOR_ENTRY",
  "entered_at": "2026-08-24T14:30:00.000Z",
  "note": "optional"
}
```

At most one active entry per `venue_id`; every `venue_id` must reference
a real canonical Venue. `ingestion/geocoding/manual-coordinate-store.mjs`
enforces this on every save (schema validation, coordinate bounds,
duplicate prevention, and a hard refusal to accept a manual coordinate
for a venue that already has `CONFIRMED`/`GEOCODED` coordinates).

### Map coordinate composition

`resolveVenueMapCoordinates(venue, manualEntry)` in
`ingestion/map/projection.mjs` is the single place precedence is decided:

1. canonical `CONFIRMED` coordinates
2. canonical `GEOCODED` coordinates
3. a valid `MANUAL_OPERATOR_ENTRY` coordinate
4. otherwise: no usable map coordinates

A manual entry never overrides an existing `CONFIRMED`/`GEOCODED`
coordinate — if one somehow still exists for a venue that has since
become `CONFIRMED`/`GEOCODED`, the canonical coordinates win and the
stale manual entry is simply never consulted (the dashboard surfaces
this case as `staleManualOverrides` for visibility, but it is never used
for eligibility). `projectObservationsToMapMarkers()` accepts an optional
`manualCoordinatesByVenueId` map/object; omitting it leaves the original
CONFIRMED/GEOCODED-only behaviour completely unchanged.

### Map eligibility

| location_status | Map eligible? |
|---|---|
| CONFIRMED | Yes |
| GEOCODED | Yes |
| ADDRESS_ONLY + valid manual entry | Yes (via the manual override) |
| ADDRESS_ONLY, no manual entry | No |
| UNRESOLVED | No |

### Manual queue generation

`npm run report:manual-coordinate-queue`
(`ingestion/geocoding/manual-coordinate-queue.mjs`) derives the
outstanding queue live from `venues/lisbon.json` / `venues/porto.json`,
excluding any venue that already has a valid entry in
`venues/manual-coordinates.json` — without altering that venue's
canonical `ADDRESS_ONLY` status. Removing a manual entry (see below)
makes the venue reappear in the next generated queue automatically.

## 4. Local-only write semantics

**Hosted deployments are read-only operator surfaces.** Manual coordinate
writes are supported ONLY from the real local repository — never from a
hosted deployment's own filesystem, which is ephemeral and is never the
canonical, Git-tracked `venues/manual-coordinates.json`.

- **Local `next dev`**: writes are allowed by default.
- **A local production build (`next build && next start`), run directly
  on your own machine, not on any hosted platform**: writes require the
  explicit `BOTM_OPERATOR_MODE=1` environment variable.
- **Vercel** (`process.env.VERCEL` set): writes are **always** rejected,
  with **no override** — this is a hard fail-closed rule, checked first,
  in `ingestion/geocoding/operator-write-gate.mjs`'s
  `operatorWritesAllowed()`. `BOTM_OPERATOR_MODE=1` does **not** change
  this.
- **Netlify** (`process.env.NETLIFY` set — this repository's real
  deployment surface, see `netlify.toml`): writes are **always**
  rejected, with **no override**, exactly like Vercel. `BOTM_OPERATOR_MODE=1`
  does **not** change this either.

Vercel and Netlify writes are both **absolutely disabled** — there is no
environment variable, flag, or configuration that makes either platform's
hosted deployment able to persist a manual coordinate. Do not read
anything in this document as implying Netlify (or Vercel) persistence is
supported; it is not, by design.

A denied write returns an explicit `403 { ok: false, error:
"WRITE_DISABLED", detail: "VERCEL_HOSTED_WRITES_DISABLED" |
"NETLIFY_HOSTED_WRITES_DISABLED" | "PRODUCTION_WRITES_REQUIRE_BOTM_OPERATOR_MODE"
}` from `app/api/operator/manual-coordinates/route.ts` — it never
pretends persistence succeeded. The browser only ever submits `venue_id`,
`latitude`, `longitude`, and an optional `note`; the endpoint never
accepts a filesystem path of any kind, and the canonical store path is
always resolved internally, never from request input.

## 5. Persistence safety

Runtime state here is **never** derived from `process.cwd()` and
**never** stored in a scratchpad, `.claude/`, `tmp/`, `temp/`,
`fixtures/`, `.next/`, `node_modules/`, browser localStorage/
sessionStorage, or any other ephemeral/runtime-directory-dependent
location. `resolveManualCoordinatesPath()` in
`ingestion/geocoding/manual-coordinate-store.mjs` resolves the canonical
path from that module's own file location
(`fileURLToPath(import.meta.url)`, walking up to the repository root) —
the same convention already used by `ingestion/geocoding/run.mjs` and
`ingestion/geocoding/manual-coordinate-queue.mjs`. Launching the dev
server from a different working directory can never change where this
module reads or writes; `tests/manual-coordinate-store.test.mjs` proves
this directly by calling it from two different `process.cwd()` states and
asserting the resolved path is identical.

Writes are atomic: a temporary sibling file
(`venues/.manual-coordinates.<uuid>.tmp`) is written, `fsync`'d, closed,
then renamed onto `venues/manual-coordinates.json` — the canonical file
is never observed half-written, and no abandoned temp file is left behind
after a successful save. A save only reports success after re-reading the
just-written file back off disk and confirming the new value is actually
there.

`venues/manual-coordinates.json` is a normal, Git-tracked repository
file — it is backed up and diffable exactly like every other file in this
repository; no separate backup mechanism exists or is needed. Git history
is the audit trail for edits/corrections (no separate audit-log field is
maintained on each entry).

## 6. Using the dashboard

1. Start the dev server: `npm run dev`, then open
   `http://localhost:3000/operator/venues`.
2. The page lists every canonical Venue still needing coordinates
   (derived live — never hardcoded), each with its evidenced address,
   current `location_status`, and — when derivable exactly from the
   committed `fixtures/map/lisbon-porto-overnight-coverage-01-live-run-proof.json`
   proof (`npm run ingest:lisbon-porto`) — the number of current
   resolved-but-unmapped listings waiting on that venue's coordinates.
   Venues are sorted by that number, descending, so the operator can fix
   the highest-payoff venues first. When that number cannot be derived
   exactly, it is omitted (shown as "—"), never estimated.
3. **Save**: enter a latitude (-90..90) and longitude (-180..180) and
   click "Save coordinates". The save is rejected if the venue already
   has authoritative `CONFIRMED`/`GEOCODED` coordinates, or if the
   coordinates are out of range/blank/NaN/Infinity/non-numeric.
4. **Edit**: an already-saved manual entry can be corrected the same way
   — `venue_id` and `method` stay the same, latitude/longitude are
   replaced, and `entered_at` is refreshed.
5. **Remove**: "Remove manual coordinates" deletes the entry. The
   canonical Venue record itself is never touched; the venue simply
   becomes non-map-eligible again (unless it now has canonical
   coordinates) and reappears in the outstanding queue.
6. Search, a city filter, and a status filter (Needs coordinates /
   Manually completed / All) narrow the list. "All" also shows
   already-`CONFIRMED`/`GEOCODED` venues, read-only, for context — the
   on-screen labels (`NEEDS COORDINATES`, `MANUAL COORDINATES SAVED`,
   `CONFIRMED`, `GEOCODED`) are presentation only and do not change the
   canonical Venue status model.

No Portugal bounding box is enforced by the schema/global validation —
latitude/longitude anywhere on Earth remain schema-valid. The UI shows a
non-blocking warning for a coordinate that looks well outside Portugal,
as a plausibility hint only.
